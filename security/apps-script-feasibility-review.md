# Offline Apps Script pure-core feasibility

Prepared 2026-10-06. The builder compiles public source locally, and a separate owner-held Google project has exercised the resulting small synthetic probe. No deployment, billing linkage, IAM change, credential creation, production database request or installed application route occurred. No private source export, real identity or business data was uploaded. A new paid backend has not been activated.

## Prepared scope and source boundary

`server/apps-script/compatibility-manifest.cjs` pins the normalized UTF-8 SHA-256 hashes and exact dependency edges of nine existing public files: legacy operations, legacy finance, identity state/tenant, enrollment registry/identity, authority, workflow and payroll. The original modules are not edited. The builder substitutes only their literal allowlisted CommonJS calls with earlier module bindings; no runtime loader, dynamic require, eval or generated-function compiler enters the artifact. Each module receives a private CommonJS closure. Workflow/payroll UMD writes to `globalThis` are contained in a detached local object.

The unchanged internal enrollment-identity dependency also defines unused Admin identity factories. Those factories are not exported by the generated namespace, instantiated with an SDK, or called. Their presence is not an installed authentication integration. The external namespace exposes only the pure operations/finance modules and narrow primitives for an explicit offline harness. A pure module's `identity` argument is already-trusted server data: accepting an object from a browser would bypass authentication and is not a supported use of this bundle.

Default configuration is deeply frozen with both legacy flags `false`, three empty binding strings and a null tariff policy. Default read/append/resolve/capture methods return `service_disabled` without inspecting the request or `Utilities`. There is no `doGet`, `doPost`, live RPC method, network library, OAuth token acquisition, token decoding, SDK initialization or log statement. The pure append routine returns an in-memory candidate and private receipt; it performs no write.

## Builder and compatibility limits

`server/apps-script/build-pure-bundle.cjs` is an offline Node tool. It reads only fixed public graph paths plus the new primitives source, rejects symlink/junction ancestors before and after reads, checks the pinned source hashes, audits unsupported APIs and syntax-checks the result with Node's VM compiler. The audit is a conservative text check tied to reviewed hashes, not a complete JavaScript security analyzer. Any original-module change requires a new compatibility review; there is no caller-supplied module or hash override.

Each build creates a fresh UUID child directory under the fixed sibling `work/apps-script-prepared`, with exclusive `wx` file creation. Existing artifacts cannot be overwritten by a repeat build. Output ancestors are checked for symlinks/junctions before creation and checked again afterward. These checks assume the local workspace is controlled by the owner; they are not a claim of race-free filesystem capability security against another process replacing ancestors between system calls.

The narrow adapter implements string-only UTF-8 `Buffer.byteLength`, SHA-256 string updates followed by hex digest, and canonical Firebase HTTPS origins up to 256 characters. Byte arrays must be dense descriptor-only arrays containing valid signed/unsigned bytes, and digest output must contain exactly 32 bytes. Unsupported encodings, algorithms, coercion, accessor-backed bytes and Utilities method drift fail closed. Native Utilities call exceptions become a fixed compatibility error. Unpaired UTF-16 surrogates are replaced with U+FFFD separately for each hash update, preserving Node's UTF-8 hash behavior rather than accidentally joining surrogates across updates.

Native bytes and hash input are bounded to the existing 8 MiB format limit. Byte length uses only the exact pure UTF-8 counter, including over-budget counts; root serialization allocates no native Blobs. SHA-256 still validates Utilities UTF-8 bytes, signed-byte shapes and fixed method references before native digesting. The format ceiling is not a proved Apps Script memory or latency budget: full hash byte-array copies and real native execution still require measurement. The origin adapter intentionally rejects many strings a general URL implementation would normalize. No browser or Node compatibility layer is supplied.

Google documents that Apps Script V8 lacks standard Node/browser APIs including URL, crypto, fetch and timers, and does not support ES modules or private/static class fields. The build rejects these unsupported additions rather than inserting a broad bypass. The genuine small probe below exercised the intrinsics used by that fixture, including `Object.hasOwn`, descriptors and freezing; untested branches and full-root limits remain separate work. [Apps Script V8 limitations](https://developers.google.com/apps-script/guides/v8-runtime#v8_runtime_limitations).

The adapter uses UTF-8 string Blobs and byte-array digests documented by Google. The genuine small probe checked native method/enum descriptors, returned byte-array prototypes, Unicode encoding and digest invocation. Native failures and all production input variants are not exhaustively proved. A native shape that violates the strict adapter will fail; weakening checks requires a separately reviewed native fixture. [Utilities reference](https://developers.google.com/apps-script/reference/utilities/utilities).

## Local verification

The dedicated suite has 27 passing synthetic cases. Node VM execution uses fake Utilities backed by Node's UTF-8 encoder and SHA-256. Fixtures establish deterministic compilation, OFF-before-inspection, static dependencies, source drift rejection, no clobber on repeat builds, genuine local directory-junction rejection, Unicode/lone-surrogate/hash parity, map/null serialization, source-version parity, own quantity and finance views, append candidates, durable receipt replay/resolve, retained UID/Google-subject authorization checks, revoked grants, strict getter/sparse rejection, capacity limits and product/row tombstones. A 1,000-record serialization and direct byte-length vectors make zero native Blob/byte/digest calls; hashing the same result then makes exactly one of each, validating the instrumentation. Stored historic report totals and archives are preserved; current tariff edits do not reprice historical lanes or merge stored observations with computed QC wages.

The existing pure operations and finance regression suites also pass: 106 cases pass across the three suites, with no failures or skips. These tests do not establish real Google sign-in, current account revocation semantics, real Utilities behavior, OAuth/IAM permissions, REST ETag contention/uncertain acknowledgement, network redirects, logging privacy, production quotas or production source compatibility. A Node compile is not a Google deployment or genuine Apps Script compilation.

The local artifact consists only of `legacy-pure.gs` and `compatibility-manifest.json` in a UUID directory outside the main/frontend tree. Its manifest records the public module hashes, generated bundle hash and OFF/empty configuration. Only the public pure code and hard-coded synthetic harness were pasted into the separate Google editor for the native proof below. A new artifact should be compiled after a reviewed source change; old artifacts remain unchanged.

All eleven stages passed in one observed 85 ms run: namespace, native method/enum/byte-array shapes, UTF-8/SHA-256 parity, OFF-before-inspection, own quantity view, appended candidate preserving old values, replay, resolve and own finance. The pasted pure bundle SHA-256 was `4e2c347928b993ff1a682ceaffe59f833e130bee05182c8bcec96982aa4ca529`; the synthetic harness was `821817fa7937a8d779ef9b913b820865805e1cebe5c453d262faae427a308e43`. The probe logged only fixed stage codes, booleans, synthetic counts and elapsed time. No database request, private production input, OAuth authorization, trigger, live RPC or web-app deployment occurred. This proves the small native fixture, not complete real-root compatibility, authentication, service capacity or installed access protection.

A separate source-OFF root transport candidate is now reviewed in `apps-script-rest-root-review.md`. It is outside this pure bundle and has no native proof or authenticated command integration yet. Genuine managed OAuth permission, fixed-root read/ETag behavior, full-root limits, current Firebase identity, browser transport, conflict/recovery and coordinated legacy cutover remain necessary before installation.

For an Apps Script-hosted UI, Google documents asynchronous `HtmlService` → `google.script.run` calls with bounded legal parameter types. Functions not declared at the script's top level are not RPC-visible. A separately reviewed top-level entry and hosted transport would therefore be needed; the prepared Node HTTP/bearer API cannot simply be pointed at this namespace. ContentService additionally redirects responses to one-time Googleusercontent URLs, which conflicts with a redirect-forbidden HTTP client. No ALLOWALL iframe workaround, JSONP, token-in-URL or exported owner OAuth token is provided. [HTML Service communication](https://developers.google.com/apps-script/guides/html/communication), [ContentService redirects](https://developers.google.com/apps-script/guides/content#redirects).

An execute-as-owner backend is a possible later investigation, not proved access: ScriptApp can supply the effective user's managed OAuth token, and RTDB accepts standard Google OAuth tokens, but the requested scopes, owner IAM, consent and linked project behavior must be validated without exporting a key. Browser callers still need genuine Firebase identity verification/current-account checks and the retained v2 grant. JWT decoding alone is insufficient. [ScriptApp OAuth](https://developers.google.com/apps-script/reference/script/script-app#getOAuthToken()), [RTDB REST authentication](https://firebase.google.com/docs/database/rest/auth), [Firebase token verification](https://firebase.google.com/docs/auth/admin/verify-id-tokens).

Future root writes must use one root ETag and conditional PUT to fence the original source, retained grant and private receipt ledger atomically. A stale ETag produces 412 without a write, and Firebase does not automatically retry it; uncertain acknowledgement must keep the same command and resolve the matching durable receipt. No such REST adapter or proof is included here. [RTDB conditional requests](https://firebase.google.com/docs/database/rest/save-data#updating_data_with_conditional_requests).

## Cost and privacy limits

Apps Script consumer quotas currently include 20,000 URL Fetch calls per day, six minutes per execution and 30 simultaneous executions per user. Owner-executed work shares the owner's limits. Full-root reads and retries would also consume the existing Firebase project's storage/download allowance; free Apps Script execution does not make Firebase traffic free. Quota exhaustion can stop service. [Apps Script quotas](https://developers.google.com/apps-script/guides/services/quotas), [Firebase pricing](https://firebase.google.com/pricing).

A no-new-charge plan requires checking the existing Firebase plan and remaining shared quota before any live stage. Linking a Cloud Billing account can upgrade Firebase to Blaze, and budget alerts do not cap charges. No linkage or billing change is part of this work. Later handlers must sanitize failures and omit tokens, root exports, identities and payroll from logs because Apps Script can record exception details. [Firebase pricing plans](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans), [Apps Script logging](https://developers.google.com/apps-script/guides/logging).
