# Enrollment first-login server candidate

Status: prepared source only, both `enabled` and `enrollmentEnabled` remain **false** on the server and canonical PageMode. Optional first-login browser wiring has also been prepared, with an explicit bound-user Google confirmation and no business storage/listener before the final verified session. No real registry, live grant, catalog seed, data migration, Rules change, IAM change, deployment or billing activation accompanies these candidates. Owner-approved private legacy account mappings are kept outside the repository; they do not establish canonical IDs or a verified owner UID. See the [browser enrollment review](enrollment-client-review.md).

The candidate exposes only `POST /v1/production/enrollment/claim` when a separately reviewed source flag explicitly permits it. The bearer header supplies a fresh Firebase token; the body must be exactly an empty JSON object. No request email, UID, Google subject, worker, division, role, project, tenant or approval selector is accepted. Successful output is only `{ok:true}`. Error output is generic, with `retrySameIdentity:true` on uncertain admission/write results. It contains no registry, profile, identity, wage or receipt.

The verifier uses `verifyIdToken(token,true)` and current `getUser(uid)` from the same fixed project SDK app. It requires an enabled verified Google user, exact token/current-provider email and subject agreement, no tenant override, and authentication/issuance within five minutes inclusive. A token refresh alone does not make old `auth_time` fresh. Email selects only an initial, exact-spelling preapproval; retained UID plus Google subject selects any subsequent claim. Another email cannot turn a retained identity into a new approval. See [Firebase token verification](https://firebase.google.com/docs/auth/admin/verify-id-tokens), [revocation checks](https://firebase.google.com/docs/auth/admin/manage-sessions#detect_id_token_revocation), [decoded token fields](https://firebase.google.com/docs/reference/admin/node/firebase-admin.auth.decodedidtoken), and [Google subject identity](https://developers.google.com/identity/openid-connect/openid-connect#an-id-tokens-payload).

The private registry permits owner-reviewed pending sewing or QC profiles only, with expiry, exact retained worker catalog binding, bounded row count/size and unique retained email/worker/UID/subject. No owner or cutting enrollment exists. One whole-tenant transaction atomically claims the approval, consumes its fixed eight admissions per minute and creates revision-one non-owner grant. It preserves products, tariffs, wages, operations, owner/tariff ledgers and other grants. Revocation/tombstones retain identity ownership; replay cannot restore an inactive grant, change modules or promote owner. A pending sewing approval requires an assigned worker in an active reviewed cycle. Exact replay may succeed after the initial approval expiry/cycle closure while its active unchanged canonical grant and retained catalog still match.

JSON validation and new registry/service copies use own-data descriptors and a serializer that does not invoke inherited `toJSON`. The three tenant integrations use that safe serializer; existing owner/tariff ledger byte/copy helpers use their own canonical primitive serializer. Tests include nonempty private ledgers and inherited object/array hooks. This is data-boundary hardening, not a claim that arbitrary runtime code, patched built-ins or SDK behavior can be made safe by a JSON codec.

The service permits one in-flight operation and at most twenty preliminary attempts per minute in process memory. Eligible approval quota is durable in the same tenant CAS, including replay; unknown callers create no UID buckets or writes. Fixed-path SDK binding is rechecked across awaits. A warm RTDB listener has a five-second cap. A repeated transaction callback aborts its candidate; at most three outer attempts reverify Auth/current user and policy. Lost/malformed acknowledgment after dispatch gives `result_unknown`; a fresh request for the same retained UID/subject reconciles rather than adding another grant. [RTDB transaction retries](https://firebase.google.com/docs/database/admin/save-data#saving_transactional_data).

Auth verification/current user lookup cannot be atomic with a database transaction. Changes immediately after the last Auth read remain a timing limit; canonical grant/approval checks still repeat inside CAS. Memory preliminary limits are per process, not fleet-wide protection. The durable quota rejects backward minute windows; it does not prove total clock order within a minute across process restarts. The service's Auth token and approval pinning is deliberately conservative across outer retries and may require a new verified request after a concurrent policy/claim update. No exact availability or cost bound is claimed.

HTTP/runtime/native coverage tests disabled source flags, accessor rejection, pre-body SDK denial, exact CORS and fixed binding, selector refusal, shared capacity, identity-only retry classification, minimal output and actual child-process timeout/disconnect. Native network tests use real Node sockets/core host with synthetic Auth/DB/service. Admin/RTDB emulator tests use actual pinned Admin SDK handles and genuine RTDB transaction retry/cache behavior with synthetic Auth verification/current-user results; they do not verify Google signatures, real UserRecord backends or production platform settings. Rules tests deny registry reads/writes to owner, sewing, QC, unknown, revoked and anonymous clients; Rules are still not installed.

The local allowlist package copies nineteen runtime sources plus four deployment files (twenty-three copies), with the unchanged pinned dependency lock. Review-only Hosting lists six exact routes, but the claim is disabled until its source flag is enabled. Functions upstream parser/logging gaps and native platform TLS/IAM/logging/container gaps remain documented in [deployment review](../server/deployment/README.md) and [native host review](native-host-review.md).

No secret belongs in source/frontend, artifacts or logs. Credentials continue to be entered only directly with their provider.
