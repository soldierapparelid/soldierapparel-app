# Prepared Apps Script root REST transport

This is a source-OFF internal transport candidate, outside the current pure bundle. No native host call, token, scope, binding, project, deployment or paid service has been activated. The successful earlier pure V8 probe does not prove this transport. Its tests use synthetic host responses and synthetic identity context only.

The factory takes a fixed trusted project/origin/tenant, managed `UrlFetchApp`/`ScriptApp` handles, clock and a trusted current-identity verifier. Browser identity objects/tokens are not accepted by this internal adapter. The verifier must implement genuine current Firebase Google-account/token checks and return the exact canonical Google identity `{projectId,uid,email,googleSubject,authTimeMs,issuedAtMs,expiresAtMs,verifiedAt}`. The adapter does not implement those checks. Worker, division, grant revision, role, profile and tenant claims are rejected rather than accepted from a browser or cached profile. The managed OAuth credential is a separate database credential, obtained only inside an enabled operation, held locally and placed only in the fixed-origin Authorization header. Candidate database scopes are `userinfo.email` and `firebase.database`, as documented by [Firebase REST authentication](https://firebase.google.com/docs/database/rest/auth); Apps Script also requires `script.external_request` for [UrlFetchApp](https://developers.google.com/apps-script/reference/url-fetch/url-fetch-app). The Firebase scope permits reads and writes even when a particular reviewed probe only performs GET. No private key or token export is needed by this design; actual effective-user IAM/scope support remains unproved.

The Google-only transport guard removes a circular dependency: the retained worker/grant must be derived from the actual root that this transport reads. It validates fixed project, descriptor-only canonical fields, enrollment-email syntax, identity chronology and expiry before credential acquisition and after the native response. All canonical identity values must stay equal; only the timestamp of a fresh `verifiedAt` observation may differ. Ordinary sessions may have an older original authentication; no five-minute enrollment requirement is introduced into this low-level transport. The trusted verifier still must actually establish verified email and make fresh current-account checks, and a caller that returns cached data violates its contract.

An authenticated internal GET is not business authorization. Its private root must be passed only to a trusted coordinator, which then calls the pure core's `capture` on that fresh root to validate retained initialization/catalog/own grant before constructing a partner DTO or write candidate. It must recapture and compare that context against every later root. Enrollment/bootstrap and owner/QC role checks require their own exact identity-state policy; a made-up Jahit grant cannot be used to obtain the first root. No coordinator, public bootstrap or grant writer is supplied by this correction.

GET uses the fixed `/.json` root and requests an ETag. PUT requires a bounded strong ETag through If-Match. Redirects are disabled, HTTP failures are muted for explicit inspection, TLS validation remains enabled, and tokens never enter URLs. These options correspond to the [UrlFetchApp reference](https://developers.google.com/apps-script/reference/url-fetch/url-fetch-app). Returned ETags must satisfy a deliberately narrow quoted base64-like shape; an incompatible native shape fails pending review.

Root JSON has a strict duplicate-decoded-key parser, dense arrays, descriptor-only serialization, unsafe-key/number checks, 8 MiB/150,000-node/depth limits and strict UTF-8 decoding from dense native bytes. Nulls, original numbers, unknown fields and numeric-map shapes survive. Empty/null roots cannot bootstrap an existing app silently. Response control-header aliases/arrays, redirect locations, compression and malformed native output fail closed. Header/content-byte prototypes and descriptors still require a genuine native fixture. The host buffers responses before this code can bound them; this is not a streaming allocation limit or proved Apps Script memory/latency budget.

A valid 412 returns conflict without retry. Exceptions, method/identity drift, malformed/nonmatching ACKs or late expiry after PUT return result_unknown and retain the same command requirement. A validated 200/equal-root response returns storageAcknowledged only, never an operation/payment receipt. [Firebase conditional requests](https://firebase.google.com/docs/database/rest/save-data#updating_data_with_conditional_requests) provide the underlying ETag comparison, not automatic retries.

Only a separate trusted command adapter may call these methods. It must derive the grant from the fresh root, compare the canonical identity/retained context/source against the strict v2 core, form the candidate including its durable exact-command receipt, issue one conditional root write with that root's ETag, and perform fresh Auth/root/grant/receipt confirmation before any UI success. Unknown ACKs must resolve the same retained command; caller-supplied replacement commands cannot overwrite a conflict. This low-level read returns a private whole root to that server adapter and must never become a public RPC result. No such integration, real Auth, managed OAuth authorization, REST call, contention/recovery proof, logging proof or production installation is claimed here.

The dedicated synthetic host suite also checks Google-only acquisition without an existing grant, rejection of cached grant/role claims, every canonical identity drift, chronology/expiry, accessor rejection and refreshed verification observations. It retains fixed-origin/managed-header, strict root/ETag/UTF-8 bounds, conditional conflict and uncertain PUT tests. Synthetic Google identity objects are fixture data, not evidence of genuine Google authentication or native permissions.

The user's no-additional-charges constraint remains binding. No Blaze, billing linkage or paid activation is included. Managed OAuth/URL Fetch and Firebase traffic still require fresh plan/quota checks before live use; this candidate cannot establish zero charges or unlimited availability. Native consent and proof are later explicit user steps, with no secrets copied into frontend, logs or chat.
