# Owner legacy page assembly — source off

`server/apps-script/build-owner-legacy-page.cjs` prepares nine owner pages from exact pinned repository HTML, JavaScript, CSS, and SVG files. It accepts only a fixed module and reviewed public web-app/Auth configuration. The default configuration is disabled. It performs no deployment, Google request, database request, or billing action.

The outer page initially initializes Firebase **App and Auth only**. It exposes its captured Google user and native RPC runner exclusively to its own child frame. The child initializes the reviewed owner-business bridge, verifies the initial-owner business read and matching binding, and opens its durable journal before mounting original controls or executing original scripts. Original Firebase Database loaders, access-control scripts, installation/service-worker hooks, and external screenshot loaders are excluded. The Database-compatible API routes only reviewed business branches and the two fixed owner photo slots. No arbitrary database endpoint, role, UID, worker, raw-root write, `eval`, or `new Function` can be selected by page inputs.

The additional trusted configuration `photosEnabled` defaults to false. With it false, no Database SDK is imported or instantiated, including during native Google tests using synthetic database URLs. With it true, the child first verifies the owner-business read, then acquires a fixed-path parent SDK gateway bound to the same actual App/Auth/user. That gateway permits only `soldierProtectedStorageV1/photos`; native SDK references never reach the original scripts. Native envelope values cross the frame boundary as bounded ASCII JSON scalars and are decoded separately in each realm. The pinned photo client validates schema 2, both distinct photo slots, hashes and receipts, and opens a journal before becoming ready. A missing or invalid photo envelope fails visibly before the original UI starts.

Auth changes dispose the business/photo bridges and facade, invoke registered legacy cleanup handlers, clear the displayed owner data, and remove the entire child frame. Fixed connection inputs cannot switch targets. Pending owner-business or photo commands have an explicit recovery button that resolves the durable original command; its form updater is not run again. Photo recovery requires the actual SDK's committed server transaction acknowledgement, including retained-envelope no-op proof; cached reads and listeners do not settle a receipt. The builder preserves draft/journal keys, removes automatic potong tombstone expiry, and prevents Laporan's automatic catalogue/schema migration and sample-data import. Original `appReady` completion is awaited before the page signals readiness.

Laporan's original `soldier/produksi` parent reads and listeners compose a verified business view with genuine current owner images. Before writing, one original updater is classified into a business-only change with canonically equal unchanged images, a photo-only change, or a compound change. Business-only writes preserve the independent photo channel; photo-only writes use the fixed photo client's revision/digest CAS and preserve the business channel. Compound changes reject visibly before either write, retaining the draft. These composed reads are observations of two separate channels, not an atomic combined snapshot. There is no distributed coordinator or silent photo scrubbing.

This remains a reviewable candidate. Twenty tests exercise synthetic Auth and real synthetic owner-business RPC/IndexedDB composition, compile every pinned transformed page, execute the retained original Laporan merge, and run the real photo client through a separate VM browser realm and a synthetic fixed SDK wire. They do **not** prove actual Google HtmlService nested-frame mounting, real Firebase SDK/Rules behavior, all original controls, printing, or operational parity. `nativeExecutionProven` and `photoWritesAvailable` remain false in build metadata.

Material limits are explicit:

- Central photos and publication require explicit `photosEnabled:true`, a complete trusted schema 2 migration, owner-only deployed Rules and actual native SDK proof. Without these prerequisites they reject visibly. Embedded owner-only purchase image fields follow the owner-business codec and working-data capacity limit; no image fields are silently discarded by the builder.
- Product rename/deletion that also alters photo keys is a compound edit and remains held. The owner must save independently supported data and photo changes one at a time; the builder has not claimed complete parity for these combined controls.
- Nota and Retur keep their existing device-local storage. They do not acquire cross-device cloud synchronization from this wrapper.
- External PNG screenshot export is unavailable; original printing controls remain pending native verification.
- Laporan refuses an unsupported non-array catalogue instead of migrating its shape automatically. Staged/QC changes remain subject to server validation and may require the existing dedicated lifecycle channel.
- The pinned repository's small SVG brand mark replaces the very large raster logo, and its existing SVG icon sprite is embedded locally. No branding or UI asset is fetched by the child.

There have been no production reads, writes, deployments, live Rules changes, or costs from preparing these files.
