# Prepared shared request admission

This internal source-OFF module supplies the request-admission callback used by the prepared synchronous legacy coordinator. Trusted assembly must provide **ScriptLock** and **ScriptProperties** from the same single Apps Script project; user/document properties, a process-local map, a different script or multiple hosts cannot satisfy the shared-state contract. There is no native global initialization, RPC, deployment, logger, live property write, identity admission or business-data access in this preparation.

A privately reviewed finite policy binds one project and policy ID to explicit start/expiry, total requests, account lookups, accepted database-response bytes and a rolling burst window. It accepts only the coordinator's exact four operation names and envelopes: read/finance/resolve reserve two 8 MiB root responses and ten Google lookups; execute reserves three responses and fourteen lookups. Caller selectors or smaller invented costs cannot buy admission. Malformed requests are rejected by the coordinator before this gate; a genuinely invalid account can consume a reservation but cannot receive a refund or reach the database.

Under the script-wide lock, the gate reads one fixed property, checks exact canonical state and policy, enforces retained counters and chronology, and persists the full reservation. It reads back the exact serialized value while still holding the lock, and only accepts after successful lock release. Different instances share the same property and cannot independently spend the last allowance. Failed later authentication or transport is never refunded. Lost acknowledgement, dropped persistence, changed readback, lost ownership, method drift or release failure denies admission; an already retained reservation remains consumed. The seed helper only constructs a string and never writes it.

Missing, malformed, expired or mismatched state cannot automatically initialize, reset, repair or refill. No calendar or deployment event replenishes it. A future owner-controlled provisioning/renewal procedure must preserve consumed allowance, use the same lock, review current aggregate service usage and unrelated callers, and prove exact persistence; regenerating a zero seed in a deployed request is prohibited. No production policy values or seed have been installed. This does not yet give indefinite availability while the owner is absent.

The counter records no token, identity, worker, command, root, tariff, wages or payment. The separate identity-admission roster and the current Google/retained grant checks remain required. Public anonymous requests can still consume Apps Script invocations, lock attempts and property-read quotas or deny service to legitimate users. The finite gate limits admitted envelopes for this one script; it cannot bound traffic through old Firebase readers, other scripts/projects, native oversized bodies already buffered by Google, retries outside this coordinator or total account-wide quotas. It is neither a bill cap nor proof that the user's workload fits the remaining free allowance. No billing activation is included.

Synthetic tests exercise retained state across factories, rolling burst boundaries, independent request/lookup/byte exhaustion, missing/malformed state, monotonic time, concurrency, uncertain persistence, readback/release failures and integration with the actual coordinator/verifier/REST modules using synthetic native hosts. Genuine ScriptLock/ScriptProperties behavior, native concurrency/quotas, installed private identity admission, current Google rejection/revocation, browser RPC, QC/corrections and production cutover are still unproved. The production read probe proved only its separate read/header path and did not run this module.

Primary API contracts: [ScriptLock](https://developers.google.com/apps-script/reference/lock/lock), [ScriptProperties](https://developers.google.com/apps-script/reference/properties/properties), and [Apps Script service quotas](https://developers.google.com/apps-script/guides/services/quotas). Current deployment checks must consult those services and the existing Firebase plan without enabling additional charges.
