# Fixed protected storage scope candidate

Prepared 7 October 2026. `server/apps-script/protected-storage-scope.cjs` is a pure **SOURCE-OFF** candidate. It makes no service calls and installs no database, Rules, grants, binding or billing changes. Its explicit `phase: "active"` describes the complete layout an approved conditional cutover would install; creating that local candidate does not activate a service. The runtime factory remains disabled unless a trusted server supplies `enabled: true`, its fixed production binding and the separately reviewed migration identity.

## Complete conditional relocation

The fixed database layout is:

```text
/soldierProtectedStorageV1
  /manifest
  /working
    /data                 strict JSON text for the root except the images branch
  /photos
    /data                 strict JSON text for original image presence and value
```

The working and photo envelopes contain exact `schemaVersion`, `phase`, project/database/tenant binding, migration ID, original root fingerprint, monotonic revision and current decoded-data checksum. Their `data` fields are scalar strings generated by the existing strict snapshot codec. Working text encodes the complete root except the images branch; photo text encodes `{present:false}` or `{present:true,value:<original JSON>}`, with a matching outer `present` flag. This protects null, empty collections and legacy array/map representation from database child-node normalization. Firebase documents that writing [null deletes data](https://firebase.google.com/docs/database/web/read-and-write). Decoding accepts only text whose strict reserialization matches its exact bytes, refusing duplicate/escaped-alias keys, whitespace and alternate numeric forms instead of silently normalizing them.

No tenant, URL, storage path or credential comes from a browser request. The complete serialized working envelope, including metadata and JSON text escaping, is limited to 2 MiB. The photo envelope is limited to 6 MiB; the complete migrated root must still satisfy the existing strict 8 MiB snapshot, node and depth limits. Limits are enforced on migration proposals, reads and writes. These format bounds support transfer accounting; they are not a promise of free capacity or unrestricted daily use.

`prepareProtectedMigration({root, binding, migrationId, expectedRootETag})` returns a complete `nextRoot`, the exact expected root ETag and a server configuration object `{migrationId, sourceRootDigest}`. The transport must issue one conditional **whole-root** write for that candidate. Every original root field moves into working data except the exact `soldier.produksi.images` branch, which moves into the photo envelope. It does not leave mutable business duplicates at the old paths. Original image absence, null, arrays, map keys, unknown fields and stored wages survive a complete reconstruction check before any proposal is returned. An occupied target namespace is refused. Malformed source data, unsupported depth/size and incomplete or mixed migrations return fixed failures; no field is discarded to make a candidate fit.

The authoritative original backup must remain private outside the production database. Storing both old and new full copies in one candidate would double the root size. The helper instead prepares an atomic relocation and a reconstruction for rollback. This relocation changes every existing client path, so the old writers must be fenced together with the application and Rules change. The helper does not prove that fence or bypass its approval.

## Working-only transport interface

`createProtectedStorageScope({enabled, binding, migration})` supplies these trusted internal methods:

| Method | Exact input | Successful result |
| --- | --- | --- |
| `readWorking` | `{working}` | `{ok:true, root, revision}` |
| `prepareWorkingWrite` | `{working, nextRoot, expectedRevision}` | `{ok:true, nextWorking}` |
| `readOwnerPhotos` | `{working, photos, identity, now}` | `{ok:true, images, photoRevision, workingRevision}` |
| `prepareOwnerPhotoWrite` | `{working, photos, identity, now, expectedWorkingRevision, expectedPhotoRevision, images}` | `{ok:true, nextPhotos, authorization}` |

The working methods require only one complete working envelope. A fixed transport should GET `/soldierProtectedStorageV1/working`, retain that response and its exact ETag, unwrap `root` for the existing lifecycle/finance modules, then wrap a successful compatible `nextRoot` and conditionally PUT only the fixed working path with that same ETag. A known conflict must not retry a mutation automatically. The wrapped revision is an additional consistency check, not a replacement for the actual transport ETag. The lifecycle's current-account, grant, receipt and post-write checks remain necessary.

A work update never fetches or writes photo payloads. A photo update cannot overwrite a concurrent work update, and a work update cannot overwrite a concurrent photo update. The working envelope rejects any reintroduced `soldier.produksi.images` property, including an empty map, so an old full snapshot cannot silently overwrite or discard the separate images. It also rejects the protected namespace inside working data, mismatched bindings or migration fingerprints, unsupported schemas, checksum drift and stale revisions.

`root` and `nextWorking` are private server objects. They contain owner finances and other preserved fields and must never be returned from a browser RPC. Existing scoped owner/Jahit/QC projection and authority checks must run before a browser view is released. Hashes are consistency evidence, not authorization or encryption; production Rules and trusted account verification protect the envelopes.

## Owner photo contract

Photo state is `{present:false}` or `{present:true,value:<original JSON>}`. The separate photo envelope always stores that complete state as strict JSON text in `data`, plus the matching outer `present` flag, preserving original absence and null without inventing defaults. The owner methods validate the current retained identity tenant, initialized owner UID and active owner grant in the supplied fresh working envelope. They also validate exact current-account identity fields and timestamps. Jahit, QC, unknown accounts, expired identities and browser role assertions cannot read or mutate photo values through these methods.

This pure module does not verify a Google token. A native transport must obtain current identity from the existing trusted verifier, authorize against a fresh working read and repeat account/grant continuity checks around the photo request. For a conditional photo write it must retain the photo ETag, enforce the expected working and photo revisions and replace only the complete photo envelope. A write whose acknowledgement or subsequent authority check is uncertain needs recoverable status; this module does not implement a durable photo request journal.

Direct Firebase client writes to either envelope or `photos/data` are incompatible with the checksum/revision contract and must be denied. Existing photo forms require an authenticated server bridge; changing a URL prefix alone would not provide that bridge. Product or series rename/delete operations that change both catalog and image keys require a reviewed atomic or durable coordination path before those operations are enabled. Other image fields elsewhere in the legacy root are preserved in working data; this partition moves only the explicitly reviewed production images branch.

## Rollback and validation

`inspectProtectedRoot({protectedRoot})` rejects incomplete layouts, legacy fields outside the fixed namespace, cross-migration partitions and invalid envelope metadata. When both partitions remain at revision one it also verifies their reconstruction against the original root fingerprint. After accepted updates each envelope carries its own current digest and revision.

`prepareProtectedRollback({protectedRoot, expectedRootETag})` reconstructs the latest original layout from a complete current protected root and returns a whole-root conditional write candidate. It preserves both the latest work and the latest images rather than using an old cached image copy. A trusted transport must read that complete root freshly and conditionally write with its exact ETag; any change after the read must conflict. Rollback requires a coordinated Rules/application review and is not run automatically.

Thirty-four synthetic tests verify exact reconstruction, unknown fields and historical money; absent/null/map/array image state; incomplete migration and wrong bindings; descriptor-safe rejection; complete-envelope byte limits; actual existing QC lifecycle and own-finance composition; stale revisions; independent concurrent photo/work changes; current owner authority; partner/QC denial; image removal/re-addition; latest-state rollback; immutable proposals; strict stored text rejection; and null-pruning wire roundtrips. The null-pruning rehearsal is synthetic, not an emulator or native conditional-write proof. These tests make no live calls and establish no real employee access, native cutover, daily quota or production deployment.
