# Prepared Apps Script current Google identity candidate

Prepared 2026-10-07. This independent synchronous candidate is default OFF, has empty project/API-key binding, and is outside the pure bundle and manual database-read probe. It has not been pasted into Google, deployed, connected to a browser route, or called against real accounts. No token, credential, account change, new OAuth scope or billing activation is included. The one-read database probe and this separate authentication candidate have different inputs and proof requirements; the probe's recorded permission and result must not be treated as evidence that this verifier ran or passed.

## Fixed request and authority boundary

`server/apps-script/current-google-identity.cjs` exposes separate enrollment/session factories. Enabled options are exactly `{enabled, binding:{projectId,apiKey}, urlFetchApp, clock}`. The API key is public project-identifying configuration, never an account credential; its grammar does not prove which project owns it. Configuration is snapshotted from own data descriptors. Default OFF returns before inspecting request fields, other options or native dependencies.

Each synchronous `verify({idToken})` sends the same unchanged original token to two fresh fixed HTTPS `accounts:lookup` POSTs, with the trusted API key as the only URL parameter. There is no owner Authorization header, token URL, refresh-token intake, caller UID/email/account selector, tenant override or alternate host. Redirects are forbidden, TLS checking is enabled, HTTP failures are inspected without reading their bodies, and the requested native fetch timeout is 20 seconds. This is not a demonstrated end-to-end deadline. The token envelope serializes only a primitive string; inherited Object/Array/String serialization hooks cannot observe or replace it.

This is the documented end-user lookup flow, distinct from an admin request using Google OAuth and account selectors. It does not require adding owner `identitytoolkit` or `cloud-platform` scopes. API-key restrictions may still prevent the request; they must not be silently relaxed. [Firebase REST account lookup](https://firebase.google.com/docs/reference/rest/auth#section-get-account-info), [lookup method](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/accounts/lookup), [Firebase API-key binding](https://firebase.google.com/docs/projects/api-keys).

The candidate checks canonical base64url segments, bounded RS256/kid/optional JWT type, exact project audience and securetoken issuer, safe subject, verified lowercase Gmail email, Google sign-in provider, one Google subject and no Auth tenant. These decoded claims are only a candidate until Google accepts the exact original string and both account observations match. Lookup's documentation does not enumerate its internal signature/audience validation algorithm: treating authenticated lookup as online token validation remains an inference, not locally implemented RSA verification or proved Admin equivalence. There is no decode-only fallback. [Firebase token verification requirements](https://firebase.google.com/docs/auth/admin/verify-id-tokens#verify_id_tokens_using_a_third-party_jwt_library).

## Current account, timing and output

Both responses must identify exactly one user matching `sub`, the same current verified email, one matching Google provider `rawId` and email, and no tenant. Output UID comes from authenticated `sub`; raw Firebase JWTs need not contain Admin's convenience `uid`. A present inconsistent `uid` or `user_id` alias is rejected. Other linked providers cannot supply fallback Google identity. Display names and `federatedId` are not identity substitutes. [DecodedIdToken reference](https://firebase.google.com/docs/reference/admin/node/firebase-admin.auth.decodedidtoken), [official provider/UserRecord mapping](https://github.com/firebase/firebase-admin-node/blob/v14.5.0/src/auth/user-record.ts).

After a bounded successful response, omitted `disabled` means false and omitted `validSince` means no observed revocation boundary, matching documented Admin defaults. Present malformed values are rejected. A canonical present boundary rejects original `auth_time < validSince`; `iat` is never substituted. Equality is accepted at second precision. A previously observed boundary cannot disappear or decrease across the two lookups. Refreshing an ID token does not reset its session's authentication time. Enrollment alone enforces the existing five-minute auth/issuance window; sessions require valid chronology and expiry without mandatory repeated login. Clock rollback, late expiry, native method drift and reentrant verification fail closed. [Official revocation check](https://github.com/firebase/firebase-admin-node/blob/v14.5.0/src/auth/base-auth.ts), [session management](https://firebase.google.com/docs/auth/admin/manage-sessions).

Token input is capped at 16 KiB; successful response bytes at 64 KiB; JSON at 4,096 values/depth 16; providers at 16. UTF-8 is decoded strictly from dense native byte arrays, then duplicate decoded keys, unsafe prototypes/numbers and malformed JSON are rejected. Native HTTP buffers before this processing guard, so it is not a download or allocation cap. No account/token result is cached. Locally held request/body/response references are cleared after each call; this is not a secure-memory-erasure guarantee.

The only success is the frozen existing eight-field internal identity DTO, plus `ok:true`. Failures contain fixed `service_disabled`, `invalid_request`, `access_denied` or `unavailable` codes. No logger or raw provider exception escapes. The identity DTO contains private account identifiers and must remain server-internal. It supplies no worker, role, grant or financial authority: the existing v2 grant/retained-subject and root-CAS chain still must derive and fence that context.

## Proof completed and still required

Thirty focused synthetic tests pass, including default OFF, exact original-token POSTs, raw JWT without UID, canonical DTO comparison against the existing mocked Admin verifier, optional-field defaults, auth-time revocation checks, account/provider changes during either lookup, strict JSON/UTF-8/budgets, native method drift, rollback/expiry, privacy, no caching and inherited serialization-hook canaries. Responses and signatures are synthetic. A fake signature plus a mocked Google 200 response proves no cryptography, account freshness or native revocation semantics.

Activation still requires genuine altered-signature/original-payload, unsigned, wrong-project/API-key, expired, revoked, disabled and deleted-account rejection; ordinary valid-account and omitted-field response fixtures; native descriptor/header/byte behavior; API-key restrictions and shared quota checks; sanitized logging proof; and reviewed browser ingress/command integration. Two lookups are observations, not atomic Auth/database authorization; the command service must repeat current identity and actual-root v2 grant checks at its existing boundaries. None of these proofs, production access protection or zero-charge availability is claimed here.
