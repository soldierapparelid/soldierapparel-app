# Prepared synchronous legacy coordinator

The internal factory connects the existing synchronous current-Google verifier, fixed-origin root transport, compatible Jahit command core and own-finance projector. It remains source-OFF with an empty project/database/tenant/key binding. It has no native global initialization, public RPC, host route, enrollment/bootstrap writer, owner/QC implementation, logger or credential persistence. It is outside the pure bundle and has not been installed in Google or the main app.

Before any Google request, a trusted shared request-admission callback must admit a fixed server budget. After genuine current Google verification, a separate trusted private identity-admission callback must admit that exact project/UID/email/Google subject before managed database credentials or a root GET. Neither callback can supply a worker, role or grant. Both require an exact synchronous boolean true. Production implementations must use a shared durable, synchronized budget and the reviewed private roster; a per-invocation counter, missing shared state, unconditional true or browser allowlist violates this contract. Those implementations are not supplied here.

The first private GET obtains the actual root and version validator. The pure core then captures the retained initialization, catalog and canonical own Jahit grant. Uninitialized, revoked, unrelated, owner/QC/potong or inconsistent grants cannot authorize this lane. A read or finance read validates its first DTO, then obtains a second fresh Google-checked root, compares the retained context and rebuilds the final DTO from that latest root. It returns only `{ok,view}`. The finance DTO preserves stored historical totals, separates unsupported history and provisional/frozen slips, and does not infer payment or combined payout.

For an append, the pure command core derives the candidate and durable exact-command receipt from the first root. One PUT uses that root's exact ETag with If-Match. The transport checks the current Google account immediately before and after the native response. A changed root/grant causes a conditional conflict, with no automatic retry. A successful storage acknowledgement still does not become UI success: a separate fresh Google-checked root must have the unchanged retained context and pass the pure core's exact receipt resolution. A lost/malformed acknowledgement, post-write revocation, missing/altered durable record, late expiry or identity drift returns result_unknown and retains the same command requirement. A separately supplied exact replay/resolve performs no extra PUT.

Requests accept only a bounded ID token and, for execute/resolve, the exact compatible append command. Caller identity, worker, tariff, total, role, URL, grant or configuration selectors are rejected before network admission. Request IDs cannot be replaced to repair an uncertain operation. Tokens are held in memory only for that invocation, sent only to the fixed Google lookup request body, and cleared with the last identity and failure marker in finally. Native host-method drift latches failure; nested calls return busy. Only fixed error codes escape.

The dedicated synthetic suite exercises the actual verifier and REST modules with synthetic native hosts, account responses, dense byte arrays, a real strict tenant fixture and simulated conditional storage. It covers scoped views, preserved money, shared admission order, current account/grant changes, concurrent root changes, exact replay, uncertain acknowledgements, independent durable confirmation, expiry and credential/root canaries. These are synthetic integration checks, not genuine Google signature rejection, effective IAM, native byte/ACK/CAS/recovery, installed shared admission, browser RPC or production role checks. The separate manually approved native read probe established a bounded root read and a compatible unquoted version-header shape; it did not exercise this coordinator or a write and does not prove protected access while the old root rules remain public.

Accepted successful read/resolve paths use at most two bounded root response bodies and ten Google lookups; a non-replayed append uses at most two root reads, one PUT response and fourteen lookups. Request admission receives those planned accepted-response envelopes. Apps Script buffers native replies before parser bounds apply, so oversized responses or unrelated live traffic can exceed a planned envelope. Actual latency, native memory, shared quotas and whole-root capacity must be measured separately. No unlimited free-operation, charge ceiling or availability guarantee follows from these constants. No billing/Blaze activation is included.

Release still requires a shared admission implementation, an authenticated browser/RPC bridge, compatible QC and ordinary corrections, actual Google rejection/revocation fixtures, retained production grants, isolated conditional-write/recovery proof, current free-capacity evidence and coordinated protection of the legacy root. The manual owner read probe and its public console wrapper must be removed before any public web-app deployment.
