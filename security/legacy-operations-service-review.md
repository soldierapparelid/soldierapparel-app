# Isolated compatible operations SDK service — source OFF

`server/production-legacy-operations-service.cjs` prepares the SDK boundary for the narrow [compatible Jahit core](legacy-operations-review.md). Optional HTTP/runtime wiring and an allowlisted package are now prepared; the source switch remains OFF and no main page is activated. It initializes no SDK app, opens no server listener and creates no credential, logger, Rules, billing change or production data. An absent/false/nonliteral enabled flag returns inert `read`, `execute` and `resolve` methods without inspecting other options, requests or SDK dependencies.

The trusted factory requires exact own-data options: enabled, projectId, databaseURL, tenantId, database, auth, clock, admit and tariffPolicy, with only an optional trusted testOnlyEmulator boolean. The policy is copied and must explicitly be the reviewed `legacy-jahit-current-v1` policy in Asia/Jakarta with good-plus-reject quantities. This adapter preserves the core's existing-current-rate behavior for a newly appended report; it does not recalculate, edit, migrate or replace old amounts. Captured policy and command values cannot be changed by an asynchronous caller mutation.

## SDK and identity binding

Auth and Database must share the same trusted Admin app object with the fixed project/database origin. Auth verification/current-user methods, Database ref method and root get/transaction/on/off/toString methods are captured and rechecked around every awaited boundary and SDK snapshot callback. The only reference is `database.ref('')`, whose canonical URL is exactly the fixed database origin plus `/`; snapshot ref URLs must also be this root. A partial legacy reference or a different app/project/path fails closed. Observable binding drift is latched for that operation.

The ordinary adapter rejects Database/Auth emulator environment and credential-file/token override presence before dispatch and after callbacks. A separate own-descriptor testOnlyEmulator opt-in is restricted to exact project `demo-soldier-security`, database `https://demo-soldier-security.firebaseio.com`, loopback `127.0.0.1:9000`, and a plain fixed fake credential whose function source and identity are pinned. No Auth emulator, override, other project/host, native credential class or arbitrary credential function can pass that hook. The adapter never invokes or initializes a credential; the standalone fixture initializes its synthetic SDK app. No credential content reader exists. This is adapter validation, not proof of a real metadata identity, IAM policy or SDK setup. Environment and application configuration cannot activate the source switch, and production deployment binding rejects demo projects.

The ordinary session identity verifier runs `verifyIdToken(token, true)` and `getUser(uid)`. Refreshed tokens may have an older original authentication time, but token chronology, expiry, verified Gmail email, current enabled UserRecord, unique Google provider and matching Google subject remain required. The command cannot select UID, worker, rate, total, role, source path or archive. The core's capture validates the full v2 identity tenant and retained UID/Google-subject grant, and admits only the bound active Jahit partner. Initialization, reviewed worker catalog and current grant are compared before and after the operation. No v1 identity downgrade is performed.

Quota receives only a frozen trusted `{projectId, uid}` after identity and core authorization. It does not receive the caller body, email, worker or financial source. A quota callback is not authority; root context and core command constraints are repeated afterward. One local in-flight slot remains occupied until the operation actually settles, including an unresolved SDK promise. This is not a global quota or a guaranteed SDK-response deadline.

## Read and root CAS

`read({idToken})` returns only the core's scoped operational view: own current assignments/reports and quantities, product labels and a non-financial source version. Rates, totals, other workers, private initialization, root data and receipt ledger are not returned. Final Auth, root context, clock and core view checks repeat before returning the view. This does not expose financial history or owner modules.

`execute({idToken, command})` copies a bounded 4 KiB command and prepares it through the pure core. For a new write, a value listener warms the SDK cache with a five-second bound. Listener content never grants access. A fresh root read and context/command validation follow admission and warming. The transaction then runs against the **entire actual root**, with local events disabled; every callback validates descriptor-only root JSON, current v2 context, expected grant/source version, active product and assignment and the exact core request again. Callback failures return undefined and do not supply an alternative root.

The root CAS preserves other root/module/legacy data, appends only the compatible new Jahit report and its assignment cache change, and retains a private external receipt under `legacyOperationReceipts/{tenantId}` in the same root mutation. The ledger is not a source from the browser and must remain private. There is no whole legacy replacement, immutable archive overwrite, historical repricing, owner grant editor or root seed route. Server-computed new report rates/totals follow the explicitly reviewed existing policy in the core.

The core limits serialized root JSON to 8 MiB, 150,000 nodes and depth 32, rejecting accessor/serialization hooks, cycles, caller sparse arrays and priority/value wrappers. Only trusted SDK snapshot/CAS representations receive a bounded descriptor-only conversion of RTDB numeric-array holes to explicit null placeholders. No business identity is inferred from those positions and caller command arrays remain strict. Object key order is canonicalized only for semantic context/acknowledgment comparison; array order and stored field types are retained. These checks occur **after** Admin SDK has fetched a snapshot or provided a transaction callback. They do not limit the SDK's network download/cache allocation before that point. This is a priority-free lane: val() does not expose child priorities, so actual source review and a prohibition on priority-producing writers remain prerequisites. Actual root capacity, writer constraints and platform controls must be reviewed before activation.

## Acknowledgment and revocation limits

Successful writes return only `{ok:true, replayed, operationId}`. The committed snapshot must match the validated candidate and retain the same v2 context. The service then verifies current Google identity again, rereads the actual root and resolves the exact durable request/created-record digest. A same-command retry is confirmed without a second append.

After transaction dispatch, lost acknowledgment, malformed committed snapshot, binding/identity/catalog drift or failed final verification returns fixed `result_unknown` with `retrySameCommand:true`. It never states that a committed report was rolled back. Preserve the original requestId, operationId, payload and expected versions; do not create a replacement identity. `resolve` is read-only and confirms only an exact retained command/current report/context; missing or altered evidence is not synthesized into a receipt.

Root CAS makes the observed identity tenant, operation source and private receipt mutation atomic **within that RTDB root**. Google Auth is independently read before and after it. Token/account revocation after the last Auth observation is not an atomic cross-service guarantee, and a write may have committed before final revocation is discovered. A legacy client that remains able to overwrite data or a grant can break this protection. Root Rules, private ledger protection, authenticated compatible writers, actual IAM/log controls and a reversible main-app cutover remain release prerequisites. No account, project, main-app, Rules, private ledger or legacy source has been changed by this preparation.
