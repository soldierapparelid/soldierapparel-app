# Compatible legacy QC and Jahit lifecycle candidate

Prepared 7 October 2026. This is a **source-OFF server candidate**, not an installed division workflow. Main HTML, production Rules/grants, billing and stored business values are unchanged. The existing pinned append-only Google bundle and its earlier genuine V8 proof remain unchanged; that proof does not cover these new modules.

## Operations and authority

`server/production-legacy-lifecycle.cjs` reads the existing full RTDB root and prepares compatible changes rather than copying historical work into empty canonical cycles. A trusted adapter must obtain the current verified Google account and CAS the full root. The candidate verifies the retained enrollment UID, Google subject, exact approved email, active grant, initialization and reviewed worker catalog. It permits one current QC module with no worker selector, or one Jahit module bound to the caller's own worker. Owner/Potong/other modules cannot borrow either lane.

The candidate supports compatible appendJahit; own Jahit edit/delete; physical count add/edit/delete; single and combined QC inspection; single and grouped QC correction; and repair completion. New count selection may select only a worker in the server's reviewed Jahit catalog. Financial, identity, host, role, grant and payroll selectors are rejected. The QC projection contains explicit operational quantities, worker labels, dates, notes, source versions and stage identifiers; no tariff, payroll, kasbon, PIN, credentials, private source fields, raw root, ledger or account identity is returned. Its source version hashes operational data and PO controls, never private money. Jahit retains the established own operational projection and separately scoped finance read.

Only stable record IDs can be selected for mutation; ID-less source rows are not given manufactured identities. Duplicate IDs, malformed collections, deletion-marker aliases, dangling/crossed relationships, archives requiring review, cancelled/paid records, future work dates and stale operational versions fail without changing input. Numeric legacy IDs and map-backed collections are preserved. Old tombstone JSON stays string-backed if it was a string; scoped deletion evidence accompanies the business changes in the same proposed root. Unrelated products, fields, archives and historical totals remain intact.

## Wages and related stock

New count snapshots use the existing historical tariff policy with explicit Asia/Jakarta midnight, including bare historical effective dates. Staged counting creates provisional slip evidence without warehouse stock. Inspection waits for the existing full-PO good-quantity gate, requires exact category totals, and links the original count, QC, warehouse and sellable rows. Existing frozen rates remain unchanged. Repair completion reduces repair-pending stock and adds its own dated frozen-rate OK movement, preserving initial versus repair earnings. Tests read the resulting root through the actual existing own-finance module rather than duplicating wage arithmetic in the test.

Own Jahit quantity correction uses the row's original stored rate and recalculates a consistent original total only when good quantity changes. Date-only correction preserves an anomalous stored total. A good-quantity change on an inconsistent stored total requires owner review; it does not silently reprice the confirmed total. Paid flags remain locked. Corrections cannot worsen counted-versus-sewn deficits or exceed assignments. Cached remaining quantities are updated only on the caller's assignments.

QC corrections retain frozen payroll, separate count dates and unknown legacy fields, including the old `kotor` spelling. They cannot remove repair earnings already moved to warehouse. Ambiguous or loose stock relationships remain owner-review cases rather than guessed links. Cascade deletion removes only the selected count and its exact QC/warehouse/sellable relationships, with compatible tombstones, and retains independent counts, photos, PO and sewing work.

## Durable receipt history and one conditional write

Private `legacyLifecycleReceipts` retain exact payload hashes, caller/grant/catalog binding and bounded collection-effect chains. Current collection heads must match the actual root. Later accepted inspection, correction or deletion extends the chain, so an earlier accepted command can still resolve without recreating a deleted row or duplicating wages. Reused IDs with different payloads/callers, corrupted or cyclic history, and changes made outside the candidate lane cannot reset or silently rebase the evidence. There is no automatic purge. Format limits remain finite: 10,000 commands and the existing 8 MiB root envelope.

`server/apps-script/legacy-lifecycle-runtime.cjs` is a separate internal coordinator with four methods: read, own readFinance, execute and resolve. It reuses the reviewed current-account verifier and fixed-root REST adapter. Shared finite admission precedes all service calls; private identity admission precedes managed OAuth/database calls. Fresh account/root/grant checks surround one full-root If-Match PUT, followed by an independent receipt read. A known 412 never retries. Lost ACK, post-write account revocation or changed durable evidence returns result_unknown with the same command retained. Replays and resolutions issue no PUT. No token persistence/logging, native host initialization, public RPC, domain exception, credential relay or live data service is included.

## Verification and release limits

Forty-eight synthetic tests cover the pure candidate (33) and actual coordinator/account/root-adapter composition (15). They verify count/inspection/repair earnings through existing finance, complete cascade isolation, append/edit/delete receipt continuity, paid and dependency fences, old totals, maps/holes, stale source/notes, wrong/revoked accounts, shared-admission ordering, conditional conflicts, lost ACK and fixed privacy errors. Host calls in these tests are synthetic; this does not establish native conditional writes, capacity, real hosted login, browser persistence or installed employee access.

All append and lifecycle changes must use the new coordinator together; the previous append-only coordinator cannot preserve these new collection heads. Current owner corrections, archive moves and old client writes need an explicit history-aware integration/reconciliation path before release. No automatic rebase is supplied. Legacy boolean stock flags, ID-less ambiguous stages and unknown payment allocations need compatibility review rather than a blanket claim of complete ordinary-work coverage. The browser codec/RPC/journal/forms and the exact pinned Google build have not yet adopted this candidate. Real hosted login, private roster/current enrollment, native isolated CAS/recovery, shared-policy provisioning/renewal, free-capacity evidence and synchronized main/Rules cutover remain required. The production database was open on its last Rules observation; login alone does not protect it.

A separate owner-only Google page has now demonstrated a real HtmlService iframe and a fixed no-data google.script.run nonce roundtrip. It does not load Firebase authentication or data services and is not the public division deployment. Its private deployment/origin observations stay outside this repository. This real channel proof is separate from both the synthetic runtime tests and any future login/production acceptance.
