# Prepared owner access management

The owner can open a separate “Kelola akses mitra dan QC” menu after the production owner view has passed its server checks. The menu lists reviewed display labels, divisions, approval status and revisions. A second click confirms a revocation. It does not show employee emails, Google subjects, UIDs, wages, raw records or credential values.

This is a source-OFF candidate. No production grant, approval, Rules, database record, Google Auth account, deployment or billing setting is changed merely by importing these files or assembling the pages. Synthetic tests are not a production installation or a native Google proof of this new menu.

## Existing transition and storage

`server/apps-script/owner-access-management.cjs` reuses `production-identity-state.cjs` for retained enrollment revocation. It does not duplicate the transition or use the Admin SDK revocation service. The latter requires an Admin SDK host; the new adapter is synchronous and uses the existing Google current-account verifier, managed fixed-scope REST transport and shared finite request admission.

`createAppsScriptOwnerAccessManagementRuntime(options)` requires `enabled`, a fixed four-field `binding` (`projectId`, `databaseURL`, `tenantId`, `apiKey`), server-only reviewed `profileLabels` (`approvalId` to display label), `urlFetchApp`, `scriptApp`, `clock`, `requestAdmission` and `identityAdmission`. Optional trusted `storageMigration` selects the protected working adapter. It is not accepted in browser requests. Without it the old full-root adapter remains the compatibility default; this default must not be mistaken for completed protected storage installation.

The runtime exposes `readAccess({idToken})`, `executeAccess({idToken,command})` and `resolveAccess({idToken,command})`. Only the retained initial owner, with a current active owner grant and current verified Google account, can receive a view or execute these methods. A client-selected role, UID, worker, destination or arbitrary patch is rejected. Missing reviewed labels fail closed. The owner is never a revocation target.

A command has exactly `kind: 'revokeAccess'`, a stable `requestId`, an approval-derived `profileId`, `expectedOwnerGrantRevision`, `expectedApprovalRevision` and `expectedGrantRevision` (null for an unclaimed approval). The server selects the retained approval and associated grant, checks the revisions and invokes the pure transition. One ETag compare-and-swap changes only that identity tenant. The retained approval is revoked and the associated grant becomes inactive; pending approvals can also be revoked before first login. Fresh login cannot reclaim a revoked approval. Google/Firebase Auth login itself remains available and subsequently fails the application's grant checks.

All business records, cutting totals, wages, payment status, private metadata, unknown fields and photos are preserved. With reviewed `storageMigration`, requests read and write only the fixed protected working path, reserving at most two 2 MiB replies for reads/resolution or three 2 MiB replies for execution. Photos are neither read nor transmitted. Without this option the old 8 MiB root limits remain. Google lookup reservations are 10 for reading/resolving and 14 for execution. Initial browser access connection performs two admitted read RPCs (four bounded storage replies, 20 lookups); this is included in the current synthetic checks and must be included in release capacity planning.

## Confirmation and recovery

A successful PUT is followed by an independent current Auth/root confirmation. A lost or malformed acknowledgment after possible dispatch returns fixed `result_unknown` with `retrySameCommand: true`; it never asserts “not saved”. ETag conflicts do not automatically retry. The retained server receipt can be resolved in a new runtime without another PUT. Resolve does not create a missing revocation. A changed command ID, target or revision cannot impersonate an existing receipt.

`createAppsScriptOwnerAccessManagementRpcGateway({enabled,binding,runtime})` exposes `dispatch` and `dispatchJson`. The native wrapper `soldierOwnerAccessRpc` passes the one JSON string to `dispatchJson`. The envelope is `{kind:'read'|'execute'|'resolve',idToken,command?}`. The gateway rejects duplicate and escaped-alias JSON keys, extra selectors, unknown fields, malformed responses and runtime handle changes. It emits only bounded normalized DTOs or fixed error codes.

`owner-access-management-codec.js` contains the bounded data-only codec. `owner-access-management-client.js` provides `createAppsScriptOwnerAccessBridge`, `createOwnerAccessController` and `mountOwnerAccessManagementPage`. The bridge captures the exact Auth user object and token method, fixed script runner, deployment and tenant. Account changes clear visible owner access data. Tokens are freshly acquired for each request and never written to a journal. The RPC timeout is 15 seconds and preserves uncertainty after possible dispatch; late callbacks cannot replace an already delivered result.

Exact commands are persisted before dispatch in an isolated IndexedDB database `soldier-owner-access-journal:v1`, using the existing transactional command store. Scope includes the fixed deployment, tenant, actual signed-in UID and owner grant revision. A lost acknowledgment or failed receipt persistence survives reload and resolves the same command. A definitely rejected first conflict may close its draft; an uncertain conflicting retry stays pending. Signout clears the display without deleting the journal. Storage failure before dispatch prevents a write.

The bootstrap pins both new browser modules and their factories. Its owner-only button loads access management lazily after production owner authorization. QC and sewing pages do not inspect its module or open its journal. A missing access backend can show a retryable connection message while already verified owner production controls remain available. An access denial or captured account/module/configuration change clears both owner channels. Terminal `_top` reload and explicit account-choice behavior remain unchanged.

## Validation and remaining work

The focused suite passes 66 tests: 37 new owner access runtime/client tests, 24 bootstrap tests and five prepared-page tests. Coverage includes owner/partner/QC boundaries, pending and claimed revocation, no self-target, financial/photo preservation, protected path limits, replay, lost acknowledgment, concurrent ETag conflict, fresh-login refusal, account changes, token wait, missing backend, module drift, duplicate JSON, persistence faults, timeout and explicit UI confirmation. The prepared pages default OFF and pin 16 browser/style sources.

Remaining release work includes review and connection of the private label map and actual retained approvals, native proof of the new owner menu, protected storage migration and consistent legacy writer installation, sustainable free admission, fresh backups/device drafts, rollback and coordinated main application/Rules installation. No actual partner grants are proven or changed by this work.
