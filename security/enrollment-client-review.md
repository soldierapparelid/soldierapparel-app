The existing seven-field PageMode configuration remains valid with enrollment false. The optional eighth field must be an own enumerable boolean data property; getters, unknown fields and malformed switches fail closed. Only the fixed source configuration reaches bootstrap. Browser storage/query/caller settings do not provide a roster, approval, identity or permission. Parent OFF cannot be combined with enrollment true. Owner wage/tariff page switches and unrelated modules are unchanged.

Bridge always requests the usual verified session first. Exact `200 {ok:true,session:...}` follows its existing validated session/journal/view path and does not open a popup or POST an enrollment claim. Only the exact initial `429 {ok:false,error:'rate_limited'}` with explicit enrollment opt-in permits a confirmation step. This response also occurs for an already-granted caller whose quota is exhausted; it is not proof of missing registration. The UI therefore uses generic confirmation text and never announces an inferred role or approval.

Bootstrap displays one generic Google confirmation button. Its click handler synchronously invokes `reauthenticateWithPopup` on the captured current User and Google provider. Popup confirmation must retain the same User object/UID, app/project/database and source configuration before/after awaits. The selected UserCredential user field must be its own data property and match that exact user; unrelated credential fields/tokens are not inspected or serialized. Account change, sign-out, source/SDK binding change, getter result or failed popup closes this attempt. Dispose/logout removes the button and settles pending confirmation without continuing network work.

Fresh authentication is required separately from refreshing the token: Firebase `auth_time` describes the original authentication, while token issuance may change on refresh. The server independently verifies freshness, current Google provider, disabled/revoked state and the private canonical approval. Client state does not grant enrollment. [Decoded token fields](https://firebase.google.com/docs/reference/admin/node/firebase-admin.auth.decodedidtoken#decodedidtokenauthtime), [current-user popup API](https://firebase.google.com/docs/reference/js/auth.md#reauthenticatewithpopup), [UserCredential](https://firebase.google.com/docs/reference/js/auth.usercredential).

After a successful confirmation, bridge force-refreshes a token and sends exactly one `POST {}` to `/v1/production/enrollment/claim` on the existing fixed command endpoint origin. The token is only in Authorization, with JSON content type, omitted credentials, CORS, no-store, no redirects and no referrer. No UID/email/worker/division/tenant/approval argument or endpoint override is accepted. Request/response waits retain captured-user and fixed-scope checks, timeouts and bounded JSON parsing; inherited/accessor response fields and duplicate/prototype JSON keys fail closed.

Only exact `200 {ok:true}` permits one fresh GET session. That new session must pass the ordinary full scope/profile/manifest validation before journal hydration or any business RTDB listener opens. Initial denial, unknown fields, redirects, malformed/oversize content, callback failure, a non-200 claim or a failed second GET all close the attempt. Even `503 result_unknown/retrySameIdentity` causes no automatic POST retry or recovery GET in this candidate. A later user-triggered reload/confirmation must keep the same account; the server's retained identity binding safely reconciles a claim whose acknowledgment was lost. There is no automatic request loop or self-activation of a revoked grant.

The bridge Auth observer is a cancellation guard during confirmation; it is not a business-data listener. Business views/journal remain behind the final verified-session boundary. The bridge disposal race settles even if an injected confirmation callback never resolves. Bootstrap performs one confirmation per page lifetime, removes event handlers and displays no emails, worker labels, wage values, tokens or raw provider/server errors during enrollment. Existing successful owner/partner session behavior and ordinary legacy source-OFF behavior remain intact.
