# Prepared operations over the existing authoritative data

`server/production-legacy-operations.cjs` is a pure, source-OFF compatible lane. It does not initialize an SDK, verify an ID token, access a database, bootstrap grants, deploy Rules, register HTTP routes, publish a view, or activate the main application. Tests use synthetic identities and business rows only. The identity DTO supplied to this pure boundary is trusted server input; its shape is not proof of Google authentication. An SDK adapter must verify the signed project token, current enabled Google account and subject, then invoke this core against the current full root in one transaction.

The existing `soldier` data stays authoritative. The candidate adds one newly identified Jahit operation to its existing product and retains its receipt in the separate, private root `legacyOperationReceipts/<tenantId>`. It does not turn old rows into canonical cycles or events, rename their IDs, assign missing identities, or copy old ongoing work into a second writable source.

## Fixed configuration and methods

`createProductionLegacyOperations({enabled,binding,clock,tariffPolicy})` requires a trusted fixed `{projectId,databaseURL,tenantId}` binding, a server UTC ISO clock and exact reviewed policy `{version:'legacy-jahit-current-v1',reviewed:true,timeZone:'Asia/Jakarta',quantityBasis:'good-plus-reject'}`. Policy approval is a deployment prerequisite; the caller cannot choose it through a command. An absent/false `enabled` descriptor returns disabled methods without inspecting other option or request fields. A malformed enabled configuration returns `unavailable`.

The server-verified identity has exactly `projectId`, `uid`, `email`, `googleSubject`, `authTimeMs`, `issuedAtMs`, `expiresAtMs` and `verifiedAt`. Ordinary unexpired Google sessions may have older original authentication times. The complete v2 identity tenant, retained admission provenance, active grant, exact claimed Google subject and reviewed Jahit worker are checked each time. Owner and QC identities cannot use this partner lane. `capture({root,identity})` returns private detached initialization/catalog/grant continuity for an SDK adapter; that result must never become an HTTP body.

`read({root,identity})` returns only `{ok:true,view}`. The fixed view contains `schemaVersion:1`, the exact own binding, own display label and active own product entries. Entries contain original product ID, `series/namaBarang/size`, original assignment IDs with assigned/good/reject/remaining quantities, and identified own sewing reports with date/good/reject/completed quantities. No worker directory, other worker, rate, total, payroll, financial detail, PIN, device information, private receipt or arbitrary legacy field is emitted. Old ID-less own rows can contribute to an unambiguous existing assignment's remaining quantity, but are not manufactured into editable operations; `hasUnlistedLegacy` indicates this limitation.

`sourceVersion` hashes only that own operational product DTO and the non-financial PO controls `poAktif`, `poJumlah`, `poTanggal` and archive count. It contains no source-backup fingerprint, private identity state, other worker's row contents, tariff or amount. This optimistic token does not prove source ownership or grant authority, and changing a tariff does not freeze a stale browser estimate. The server selects the reviewed current rate at the actual append.

`append({root,identity,command})` requires exactly `{kind:'appendJahit',requestId,operationId,productId,assignmentId,expectedGrantRevision,expectedSourceVersion,workDate,good,reject}`. `workDate` is a real date or `null` for the server's Jakarta calendar date. Future work dates, zero total quantity, fractional/negative PCS, overflow, stale grants, changed source versions, another worker's assignment and exceeded remaining quantities are rejected. Browser worker/role/tariff/total/source-root overrides are rejected. The new operation ID is explicitly selected for this new request and bound to its durable payload; no identity is derived for any old row.

The private success contains `{ok:true,next,receipt:{ok:true,replayed,operationId}}`. `next` is the candidate full root for a trusted root CAS, not a public response. `resolve` returns only the minimal matching receipt and never appends a missing operation. Missing receipts return `result_unknown`; retrying after an ambiguous write must use the same request ID, operation ID and payload.

## Legacy rates and untouched old money

The existing Jahit append handler calls `getTarifJahit` without a historical date. That handler uses the current sanitized product key, falling back to the current raw product key when the former is falsy. The explicit reviewed policy reproduces that selection from the bound worker's current server source. `ProductionPayroll.rateFor` validates the chosen current rate through a detached single-current-rate input, rather than applying the old history table to a backdated new report. A missing, zero, negative, non-finite or unsupported rate blocks the append. The new row stores that rate and good-quantity multiplication, with no rounding or payment action.

Every pre-existing row's quantity, tariff, total, paid marker, optional fields, unknown fields and archive remain untouched, including a historical total that disagrees with quantity times rate. No old record is repriced. Only the new row, the selected assignment's compatibility remaining/edit timestamp and the new private receipt change. A null work date uses UTC+7 explicitly, independent of the process's default timezone. An explicit backdate retains the command's date but uses the reviewed current append rate, matching this specific existing Jahit input behavior.

## Concurrency and receipts

The complete fixed v2 tenant must be present under `authorityTenants/<tenantId>`. A trusted adapter must perform the append against the common RTDB root, where that identity tenant, the existing product and the external private ledger are observed together. The core must rerun inside every SDK transaction callback. Separate product and grant transactions, a whole cached browser JSON replacement, or a multi-path update based on an earlier read do not provide this fence.

Receipts retain exact payload, UID/Google subject/worker/grant, immutable initialization/catalog guard, private PO/assignment guards and the digest of the actual newly created stored row. The private PO guard includes archive content and never appears in the public source version or acknowledgment. Replay/resolve checks current active scope and exact actual row. A changed/reopened PO, reassignment, revoked grant, bootstrap/catalog replacement, reused request with a different payload, changed/deleted created row or future receipt timestamp is rejected. A receipt cannot restore an intentionally deleted or edited row. Legitimate changes elsewhere in the root are preserved and do not invalidate confirmation.

Owner deletion controls are fenced from that same root: `soldier/produksi_deleted_ids` accepts a bounded JSON string or array/map of explicit source product IDs, and `soldier/produksi_deletions` accepts a bounded JSON string/map of nonnegative integer timestamps. Duplicate and escaped-alias JSON keys, unsupported formats or over-budget markers fail closed. Explicit deleted products are excluded even while their array row still exists. Only the exact `productId|jahit|id:operationId` tombstone is an operation identity: it excludes that exact row from operational progress without deleting or repricing the raw stored row, and prohibits new operation-ID reuse or replay after deletion. Name, quantity/date fingerprint and link tombstones are retained untouched and never interpreted as operation identities. Raw marker strings remain byte-identical in the candidate root.

Owner source modules already use fresh transactional three-way merges. Identified independent appends can coexist with this server append. A concurrent edit to a legacy ID-less field aborts instead of overwriting the server operation. This pure test is useful evidence for the merge behavior, not proof that an old browser version or an arbitrary owner restore path cannot replace source data. Cutover must revoke legacy partner whole-root access and retain/quarantine pending old drafts without blindly replaying them.

## Bounds and remaining release work

Descriptor-only root copying/serialization is bounded at 8 MiB, 150,000 nodes and depth 32. Non-JSON hooks, reserved object keys, sparse arrays, negative zero and RTDB priority/value wrappers are rejected rather than normalized away. Current sources require a map-shaped production parent, unique stable product/assignment IDs, integer assignment quantities, explicit worker IDs for current sewing rows, unambiguous existing `ProductionWorkflow.assignmentProgress`, an active `poAktif:true` product, and a current bound worker catalog row. These are supported-shape constraints, not a finding that historical records outside them should be changed or deleted. The manifest fails closed on an unsupported relevant product; it never reports a partial view as complete.

There are at most 2,000 products, 40,000 rows per collection, 128 source workers, 10,000 retained commands per tenant and a 1 MiB public view. Full-root source/receipt growth or unrelated owner image updates can exhaust the root budget or cause transaction contention. Receipts are not silently purged to reclaim capacity. Publishing another full backup under the same RTDB root also consumes this budget; a local private backup is not a second writable business source.

This increment supports only own operational reads and one new sewing append. It does not implement partner edit/delete, QC count/inspection/repair, live own wages/slips/kasbon, owner v2 bootstrap UI, source-proof deployment, real Auth/SDK integration, Rules installation, browser cutover, paid hosting, Shopee or AI credentials. Existing owner modules must remain authenticated and operate on the same source; partner/QC commands must move to narrow server operations before the broad legacy database access closes. Immutable direct stored history is a separate historical snapshot and does not replace the current own slip or follow future owner edits.

Validation: `node --test tests/production-legacy-operations.test.cjs` passes 40 synthetic cases covering isolation, preserved old money, current-rate semantics, Jakarta dates, replay/receipt confirmation, revoked/foreign/forged authority, stale PO/source, explicit deletion races/reuse, marker format and duplicate-key hazards, request overrides, map/ID-less preservation, numeric-key normalization hazards, root limits and actual existing three-way owner merge. No production mutation, remote grant, secret or real financial value is used by those tests.
